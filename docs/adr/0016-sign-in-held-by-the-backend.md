# Sign-in is held by the backend, as a confidential client, and phones hold a FamilyHub session

The family app signed in with MSAL in the browser, as a single-page app (ADR 0010, AB#56). Entra gives a single-page app's refresh token 24 hours, whatever the token lifetime policy says, and after that MSAL tries to renew in a hidden frame. That failed on Ross's phone every day (measured 26 November 2026), most likely because of External ID's known issue with Google and a `username` parameter in silent sign-in, and because Google won't load inside a frame. So the app asked him to sign in again every day.

Now the backend signs Members in. The FamilyHub app registration is a confidential client too, with a Web redirect URI on the API and a client secret. The secret is kept in the Key Vault, and the function app reads it through a Key Vault reference, with its managed identity allowed to read that one secret only. `GET /auth/sign-in` starts an authorisation code flow with PKCE, and the tenant posts the code back to `/auth/callback` as a form, so it's never in a URL. The backend redeems the code with the secret, then sends the browser back to the family app's `/auth/done` with a one-time code, which the app swaps for a session token at `POST /auth/session`. An account that isn't the Household's swaps its code for its email address and no session, for screen B, and its tokens aren't kept.

A session token is 32 random bytes, sent as a bearer token. Only its SHA-256 hash is kept, in Cosmos DB's `sessions` container, with the Member's MSAL token cache. At most once a day, a call with it forces a refresh from Entra. A web app's refresh token lasts 90 days unused and slides with each use, so a phone used at least every few months never signs out, and Entra decides when a session ends: 90 days unused, or "Revoke sessions" on the account in the tenant. If Entra says the sign-in is over (`invalid_grant` or `interaction_required`), the session is deleted and the phone gets a 401. Any other failure, Entra not answering or an expired secret, lets the Member in and asks again later, so a problem of the backend's never signs everyone out. Every call still checks the account against the Household's list (ADR 0014), so removing an account locks out its phones. `scripts/sessions.py` lists and ends sessions, for a lost or replaced phone. Sign-in flows (10 minutes), one-time codes (2 minutes) and sessions (90 days, starting again at each check) share the container, each with its own ttl, so nothing needs cookies.

The API still takes Entra access tokens, for the Hub's certificate sign-in and the scripts. The family app moves over in AB#94, and drops MSAL.

Security is kept to what a shopping list needs: a stolen session token gives one Member's lists until it's ended or unused for 90 days, which is the same kind of exposure as MSAL's refresh token in the browser's local storage was.

Partly replaces ADR 0010, where the family app signed in with MSAL in the browser and sent Entra's tokens to the API.

## Considered Options

- **Keep MSAL in the app, and renew with a full-page redirect instead of a hidden frame:** a few hours' work, but it still depends on the tenant's own session lasting, and flashes a redirect on opening once a day.
- **The backend's own session token after one sign-in in the app, with no confidential client:** less to set up, with no secret, but Entra would have no say once a phone had a session, so revoking an account in the tenant wouldn't reach it. Ross chose a confidential client, done properly without over-engineering it.
- **HttpOnly cookies instead of a bearer token, as a "backend for frontend" usually has:** script on the page couldn't read them, but the family app (Static Web Apps) and the API (Functions) are on different sites, so the cookie would be a third-party one. Putting both on one domain needs custom domains on both. Not worth it for a shopping list.
- **A certificate instead of a client secret, or a federated credential with the function app's managed identity:** no secret to renew, but a certificate is more code to load, and the app registration is in the External ID tenant while the managed identity is in the subscription's own, which managed identity federation doesn't cover.
- **Encrypting the token cache in the app before it's stored:** Cosmos DB already encrypts at rest, and only the function app's managed identity and Ross can read the container.
- **Register the app as "Mobile and desktop" to get a 90-day refresh token in the browser:** Entra only lets a browser redeem tokens cross-origin for a single-page app registration (AADSTS9002326).
- **A custom domain for the tenant's sign-in pages, so the hidden frame's cookies count as first-party:** External ID needs Azure Front Door for that, which isn't free.
